# 2단계: Judge Worker 설계 기록

## 1. 채점 로직과 큐 처리를 분리했다

`judge.py`는 "소스 + 문제 → 판정"만 담당하고 Redis를 모른다. `worker.py`는 큐에서 꺼내고 결과를 넣는 일만 한다.
덕분에 채점 로직은 Redis 없이 단위 테스트할 수 있고, 나중에 큐를 Kafka나 RabbitMQ로 바꿔도 `judge.py`는 그대로 둘 수 있다.

## 2. Java는 메모리 제한 방식을 다르게 했다

처음에는 모든 언어에 `RLIMIT_AS`(주소 공간 제한)를 걸었는데, JVM은 실제 사용량과 무관하게 시작할 때 가상 메모리를 크게 예약해서
**정답 코드도 실행 자체가 실패**했다.

- 해결: runner에 `--no-as-limit` 옵션을 추가하고, Java는 `-Xmx`로 힙을 제한한 뒤 실제 사용량(`ru_maxrss`)으로만 MLE를 판정
- 대부분의 온라인 저지가 Java에 별도 메모리 정책을 두는 이유를 직접 확인한 사례

## 3. 언어별 시간 보정

같은 알고리즘이라도 Python은 C++보다 수십 배 느리다. 문제의 시간 제한을 그대로 쓰면 Python 사용자는 풀 수 없는 문제가 생긴다.
백준과 비슷하게 `제한 × 배수 + 보너스` 방식으로 보정했다 (Python ×3+2초, Java ×2+1초).

## 4. 테스트 데이터도 검증해야 한다

int 오버플로를 잡는 테스트케이스로 `1000000000 1000000000`을 넣었는데, 합계 20억은 int 최댓값(약 21.4억) 안이라
**오답 코드가 AC를 받았다.** 테스트가 이를 잡아냈고, `2000000000 2000000000`으로 수정했다.
채점 시스템에서는 코드만큼 테스트케이스 품질이 중요하다는 걸 확인했다.

## 5. 알려진 한계와 개선 계획

| 한계 | 개선 계획 |
|---|---|
| `BRPOP`은 꺼내는 순간 큐에서 사라져, 채점 중 워커가 죽으면 제출이 유실됨 | `BLMOVE`로 processing 리스트에 옮겨두는 Reliable Queue 패턴 또는 Redis Streams + consumer group |
| 결과 큐 하나를 여러 소비자가 공유 | 3단계에서 API 서버가 결과를 DB에 저장하고 클라이언트는 SSE로 수신 |
| 제출 코드가 파일 시스템·네트워크에 접근 가능 | 5단계에서 컨테이너 격리 + seccomp + cgroup |
| 워커 1대 | 컨테이너 수평 확장 (`docker compose up --scale judge-worker=N`) 후 처리량 측정 |
