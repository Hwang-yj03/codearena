# 4단계: 프론트엔드

## 1. CORS 대신 같은 출처

개발 중에는 Vite 개발 서버가 `/api` 요청을 `localhost:8080`으로 프록시한다. 브라우저 입장에서는 같은 출처라 CORS 설정이 필요 없다.
배포할 때도 Nginx가 정적 파일과 `/api`를 같은 도메인에서 서빙하게 할 예정이라, API 서버에 CORS 허용 목록을 둘 필요가 없다.

## 2. 비동기 채점 결과 받기: 폴링

제출 API는 `202 Accepted`만 돌려주고 채점은 나중에 끝난다. TanStack Query의 `refetchInterval`로 1초마다 조회하다가 `status`가 `DONE`이 되면 멈춘다.

```ts
refetchInterval: (query) => (query.state.data?.status === 'DONE' ? false : 1000)
```

SSE나 WebSocket이 더 실시간이지만, 채점은 보통 1~3초 안에 끝나고 서버 구현이 단순해서 MVP에는 폴링을 택했다.
API 서버를 여러 대로 늘리면 SSE 연결과 결과 수신 서버가 다를 수 있어서, 그때는 Redis Pub/Sub이 추가로 필요하다.

## 3. 오래된 클로저 버그

Monaco 에디터의 Ctrl+Enter 단축키는 에디터가 처음 만들어질 때 **한 번만** 등록된다.
처음 구현에서는 그때의 제출 함수를 그대로 넘겨서, 단축키를 누르면 **에디터를 처음 열었을 때의 코드**가 제출되거나 제출이 막혔다.

- 발견: 헤드리스 브라우저로 전체 흐름을 자동 실행하던 중, Ctrl+Enter 제출만 결과가 오지 않았다. 목(mock) 서버에서 실제 제출된 소스를 출력해 원인을 확인했다.
- 해결: 단축키는 `ref`를 거쳐 항상 최신 함수를 부르게 하고, 제출 시점의 코드는 `mutate({ language, code })` 인자로 넘겼다.

## 4. Monaco를 번들에 포함

`@monaco-editor/react`는 기본으로 Monaco를 CDN(jsdelivr)에서 받아온다. CDN이 막힌 사내망이나 오프라인에서는 에디터가 뜨지 않아서 npm 패키지를 번들에 넣었다.

- Monaco 0.57은 패키지 내부에서 워커를 `new URL('...?esm', import.meta.url)`로 불러오는데, Vite 8(Rolldown)이 이를 번들링하지 못해 페이지가 멈췄다.
- 워커 진입 파일(`editor.worker.ts`)을 프로젝트 안에 두고 `?worker`로 불러와 `MonacoEnvironment.getWorker`에 연결해 해결했다. 패키지 `exports` 규칙 때문에 경로는 `monaco-editor/editor/editor.worker.js` 형태여야 한다.
- 에디터는 문제 화면에서만 지연 로딩(`React.lazy`)해서 첫 화면 번들은 약 100KB(gzip)로 유지했다.
- 언어 서버가 없어 자동 완성이 단어 나열뿐이고 Enter로 추천어가 입력되는 문제가 있어 자동 추천을 껐다.

## 5. 토큰 저장 위치

| 방식 | 장점 | 단점 |
|---|---|---|
| localStorage (현재) | 구현이 단순, API 서버가 stateless 유지 | XSS가 생기면 토큰이 탈취될 수 있음 |
| httpOnly 쿠키 | 스크립트로 읽을 수 없음 | CSRF 대응 필요, 서버 설정 증가 |

React가 기본으로 출력을 이스케이프하고, `dangerouslySetInnerHTML`을 쓰지 않으며, 토큰 수명을 1시간으로 짧게 둬서 위험을 줄였다.
Refresh Token을 도입할 때 Refresh Token만 httpOnly 쿠키로 옮기는 방식을 검토한다.

## 6. 작은 보안·사용성 처리

- **오픈 리다이렉트 방지:** 로그인 후 `?next=` 주소로 돌아갈 때 `/`로 시작하는 내부 경로만 허용한다 (`//evil.com` 차단). 테스트로 보장한다.
- **401 처리:** 인증이 필요한 요청이 401을 받으면 저장된 토큰을 지워 로그아웃 상태로 돌린다. 토큰 만료 시각이 되면 자동으로 로그아웃한다.
- **작성 중인 코드 보존:** 문제·언어별로 코드를 브라우저에 저장해 새로고침해도 사라지지 않는다.
- **접근성:** 입력창 라벨과 도움말을 분리해 `aria-describedby`로 연결했다. 테스트가 "닉네임 2~20자…"를 통째로 라벨로 읽는 문제를 잡아냈다. 채점 결과는 `aria-live`로 스크린리더에 알린다.

## 7. 디자인 원칙

- 색은 판정을 말할 때만 쓴다 (맞았습니다 초록, 틀렸습니다 빨강, 시간·메모리 초과 황색, 에러 보라). 나머지는 남색 잉크와 흰 바탕.
- 화면에서 가장 크게 보이는 건 채점 결과 한 가지. 결과가 도착할 때 판정 문구와 테스트케이스 막대만 한 번 움직인다. 모션 감소 설정을 존중한다.
- 문제 목록과 제출 기록은 표 데이터라 카드 대신 표로 보여준다.

## 8. 검증

- Vitest + Testing Library 15개: API 에러 처리, 토큰 해석, 결과 패널, 로그인·회원가입 화면, 오픈 리다이렉트
- 헤드리스 Chrome으로 목 API 서버에 붙여 전체 흐름(목록 → 로그인 → 제출 → 채점 중 → AC/WA/CE → 내 제출, 모바일)을 실행하고 콘솔 에러가 없는지 확인
